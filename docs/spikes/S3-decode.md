# S3 — один проход декодирования для анализа

**Вопрос.** Успевает ли один вызов ffmpeg (proxy 540p + wav 16 кГц моно + кадры 160×90 gray, 4 к/с, в pipe с метриками в Python) работать на скорости **≥ 12× реального времени** на CPU для 1080p H.264 (цель 15×) и укладываться в **< 1,5 ГБ** памяти (§5.1, §5.3)?

**Короткий ответ (пока только Mac).** Узкое место — не Python и не pipe, а само декодирование и кодирование proxy. Python-часть (резкость, яркость, движение, тряска) занимает 1–3% одного ядра при 4 к/с и ≤ 14% даже при 25 к/с, pipe ffmpeg не тормозит (скорость с метриками / без pipe = 0,997–1,019), пик памяти 265–770 МБ. А вот порог скорости на **M1 не пройден**: 11,1× на синтетическом 1080p25 с 20 Мбит/с и 6,9× на 1080p50 с 28 Мбит/с. Но это **Mac, не для решения**, а синтетика с шумом (тяжелее реальной съёмки по CABAC-нагрузке). Решение по скорости принимается по прогону на эталонном ПК (Ryzen 5 5600H) с реальными файлами; команды в конце.

Все числа ниже — **Mac, не для решения**: Apple M1 (8 ядер, 8 ГБ), ffmpeg 9.0.2 (Homebrew), OpenCV 5.0. Сырые данные: `spikes/results/s3/summary-darwin-20261107T193548Z.json`, по прогону — `darwin-<источник>-<hw>-<режим>-<к/с>fps-*.json`, разбор по этапам — `attrib-darwin-*.json`.

## Что мерили

- **Исходники (синтетика, `spikes/s3_decode/sources.py`).** 1080p25 H.264, 20 Мбит/с, 240 с; 1080p50 H.264, 28 Мбит/с, 240 с; **4K30 HEVC main10, BT.2020 + HLG (`arib-std-b67`), 45 Мбит/с, 90 с, поворот −90° через display matrix (как портретная съёмка iPhone)**. Во все картинки добавлен временный шум (иначе `testsrc2` декодируется нереально быстро), а в левом верхнем углу *сохранённого* кадра нарисован белый квадрат для проверки ориентации.
- **4K HLG — синтетика.** Пиксели — SDR-картинка, помеченная как HLG; совпадают только теги, кодек и поворот. **Реального файла с телефона и реального файла с камеры пока нет, шаг брифа «по одному реальному файлу каждого типа» остаётся открытым** (`bench_decode --real метка=путь`).
- **Один вызов ffmpeg, три выхода** (`single_pass.py`): `proxy.mp4` (libx264 veryfast, CRF 26, `-g` = 1 с, CFR по ближайшей стандартной частоте, 540 по *короткой* стороне, SDR-теги BT.709), `audio.wav` (pcm_s16le, 16 кГц, моно), `rawvideo` gray 160×90 (90×160 для портрета) 4 к/с в `pipe:1`. `-progress` идёт в stderr и разбирается в потоке. Python читает pipe порциями по 64 кадра (≈ 0,9 МБ), копит метрики и пишет `frames.npz`.
- **Режимы:** `full` (читать и считать), `drain` (читать и выбросить), `none` (без выхода в pipe). Разница `full` / `none` показывает, тормозит ли Python ffmpeg. Плюс `full` при 25 к/с метрик (запас по нагрузке на Python).
- **Декодирование:** CPU и `-hwaccel videotoolbox` (на Windows — `d3d11va`).
- **Измерения:** время стены / длительность медиа (× реального времени); CPU ffmpeg (rusage ребёнка) и Python (`cpu_times`) в % одного ядра; пик RSS ffmpeg и Python (psutil, 0,1 с) и пик суммы.
- **Проверка выходов** на каждом прогоне: кодек, размер (короткая сторона 540), `pix_fmt`, теги цвета proxy, отсутствие остаточного поворота, квадрат в ожидаемой четверти кадра, wav 16 кГц моно.

**Куда уходит время (1080p25 CPU, первые 60 с, `attribute.py`):** только декодирование 18,5×; + масштаб до 540p 16,7×; + x264 ultrafast 15,0×; superfast 12,3×; veryfast 12,1×. То есть на M1 половина потолка — декодер (синтетический шум 20 Мбит/с — худший случай), а x264 veryfast съедает ещё ~30%. На 4K HEVC 10 бит декодер даёт всего 3,3×, дальше почти ничего не добавляется (масштаб 2,9×, x264 2,7–2,8×). Для 4K главный рычаг — аппаратное декодирование, а не пресет.

## Zscale / тонемаппинг

**В Homebrew-сборке нет `zscale` (нет libzimg)**, поэтому на Mac проверен только **запасной путь**: `colorspace=all=bt709:iall=bt2020` с принудительной пометкой BT.709 (HLG-сигнал трактуется как гамма BT.709 — для HLG это штатная «обратная совместимость», но без сжатия светов). Проверено: теги, размер, ориентация. **Путь `zscale+tonemap` (hable) собран, но не запускался ни разу**: `zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p`. Сборка gyan «full» zscale содержит; `single_pass.py --tonemap auto` сам выбирает путь по `ffmpeg -filters`, а `bench_decode` печатает выбранный путь. Масштаб до 540p идёт *до* тонемаппинга (в 4 раза дешевле). На Windows надо проверить скорость и вид кадра (света, цвет); при ощутимой потере скорости запасной путь допустим для proxy-метрик.

## Решения (предварительные)

- **Proxy: 540 по короткой стороне**, h264 veryfast CRF 26, `-g` = 1 с. Для 4K и портрета выход 540×960 при тех же затратах, что 960×540. Если на ПК не дойдёт до 12×, первым рычагом будет пресет `superfast`/`ultrafast` (+3–25% на M1), не разрешение: декодер всё равно дороже.
- **Метрики: 4 к/с, 160×90.** Python съедает 1–3% ядра; 25 к/с стоили бы 4–14% — запас огромный, но выигрыша для детектора сцен и качества кадра нет.
- **ETA по умолчанию:** пока нет данных с эталонного ПК, статический профиль без GPU: **10× для 1080p ≤ 30 к/с, 6× для 1080p50, 3× для 4K HEVC**; с `d3d11va` на 4K — 4×. Первая оценка по §5.1 всё равно перезаписывается измеренной скоростью после 60 с работы.
- **Ожидаемое время анализа 3 ч 40 мин сырья (этапы 1 и 1b)** по числам M1: 1080p25 ≈ 20 мин, 1080p50 ≈ 32 мин, 4K ≈ 53–79 мин. Для §5.3 (15× = 15 мин) это хуже в 1,3–2 раза на 1080p; **бюджет в 20–25 минут держится только для 1080p25**. Окончательные числа — с Windows.

## Риски и что не проверено

- **Не измерено на Windows**: ни `d3d11va`, ни реальный CPU эталонного ПК, ни `zscale`. M1 с 8 быстрыми ядрами и Ryzen 5 5600H (6 ядер / 12 потоков, при ~6 ГБ ОЗУ) несравнимы.
- **Нет реальных файлов** с камеры и телефона. Синтетический шум искажает нагрузку (по CABAC тяжелее реальной съёмки, по движению и межкадровой компенсации — легче). 4K HLG-пиксели — не HLG.
- **VFR и неровные таймстемпы** телефонов не проверены: `fps=` в графе приводит к ближайшей стандартной частоте, поведение на реальном VFR не видели.
- Файлы **без звука** поддержаны в командной строке (нет выхода wav), но тестом не покрыты. Поворот ±90° проверен только для −90°; 180° — только в функции ожидания.
- Память на ноутбуке с ~1,5 ГБ свободной ОЗУ: ffmpeg 4K HEVC занимал 662–723 МБ, 1080p — около 230 МБ, Python ≤ 50 МБ. Для 3 ч 40 мин метрики занимают ≈ 2 МБ (52 800 кадров × 4 float32). Запас есть, но x265 при *генерации* 4K-исходника на ноутбуке может не влезть и идёт ≈ 10 мин даже на M1.
- Пик памяти измеряется выборкой каждые 0,1 с.
- Скорость Mac при зафиксированной температуре и параллельной нагрузке не контролировалась; повтор по одному прогону (`--repeat 1`).

## Как запустить на Windows-ПК (эталонный ноутбук)

Ryzen 5 5600H, GTX 1650, ~6 ГБ ОЗУ, ffmpeg 9.0.2 gyan full, репозиторий `C:\Users\oshis\mojo_studio`.

```
cd C:\Users\oshis\mojo_studio
.venv\Scripts\pip install -e ".[dev,spikes]"
ffmpeg -hide_banner -filters | findstr zscale
```

Исходники весят ~2 ГБ и генерируются долго (особенно 4K), поэтому лучше скопировать с Mac готовые `spikes/data/s3/h264_1080p25.mp4`, `h264_1080p50.mp4`, `hevc_4k_hlg_rot.mp4` (команда `bench_decode` не пересоздаёт существующие файлы). Иначе — короткие версии:

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --prepare-only --dur-1080 120 --dur-4k 40
```

Основной прогон (CPU и `d3d11va`, все режимы, ~15–25 мин). На ноутбуке с ~1,5 ГБ свободной ОЗУ закройте браузер и прочее:

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --hwaccels none,d3d11va --repeat 2
```

Реальные файлы (путь с кириллицей и пробелами — в кавычках; метка латиницей):

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --only "" --hwaccels none,d3d11va --real "camera=D:\Свадьба\камера 1\C0001.MP4" --real "iphone=D:\Свадьба\телефон\IMG_0001.MOV"
```

Разбор по этапам и одиночный проход (с `cuda` при желании):

```
.venv\Scripts\python -m spikes.s3_decode.attribute spikes\data\s3\h264_1080p25.mp4
.venv\Scripts\python -m spikes.s3_decode.attribute spikes\data\s3\hevc_4k_hlg_rot.mp4 --hwaccel d3d11va
.venv\Scripts\python -m spikes.s3_decode.single_pass "D:\Свадьба\клип.mp4" --out-dir "D:\out" --hwaccel d3d11va --tonemap zscale
```

Сначала запускать без GPU и с GPU на одном и том же ПК, затем (если есть) на машине без дискретной карты. Коммитить только `spikes/results/s3/*.json`, не `spikes/data/`. Что смотреть: `x_rt` в `summary-win-*.json` против 12 / 15; `tonemap` должен быть `zscale`; `verify.proxy_trc` = `bt709`, `orientation_ok` = true для синтетического 4K и визуально для реального файла с телефона; `d3d11va` на H.264 может оказаться медленнее CPU, как videotoolbox на Mac, а на 4K HEVC 10 бит — быстрее.
