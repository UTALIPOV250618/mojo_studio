# S3 — один проход декодирования для анализа

**Вопрос.** Успевает ли один вызов ffmpeg (proxy 540p + wav 16 кГц моно + кадры 160×90 gray, 4 к/с, в pipe с метриками в Python) работать на скорости **≥ 12× реального времени** на CPU для 1080p H.264 (цель 15×) и укладываться в **< 1,5 ГБ** памяти (§5.1, §5.3)?

**Короткий ответ (пока только Mac).** Python-часть (резкость, яркость, движение, тряска) занимает 1–3% одного ядра при 4 к/с и ≤ 14% даже при 25 к/с, pipe ffmpeg не тормозит (скорость с метриками / без pipe = 0,986–1,010), пик памяти 196–790 МБ. А порог скорости на **M1 не пройден ни на одном 1080p**: 11,1× на синтетическом 1080p25 с 20 Мбит/с, 6,9× на 1080p50 с 28 Мбит/с и **3,7× на 1080p50 с 80 Мбит/с** (длинный GOP, движение по всему кадру, как у тяжёлых камер XAVC). Узкое место — декодирование и кодирование proxy, не Python. Всё это **Mac, не для решения**; окончательный вердикт даёт прогон на эталонном ПК (Ryzen 5 5600H) с реальными файлами; команды в конце. Важно: скорость сильно зависит от битрейта, и «15× для 1080p H.264» нельзя считать общим числом — оно верно максимум для лёгких файлов (≈ 20 Мбит/с и ниже).

Все числа ниже — **Mac, не для решения**: Apple M1 (8 ядер, 8 ГБ), ffmpeg 9.0.2 (Homebrew), OpenCV 5.0. Сырые данные: `spikes/results/s3/summary-darwin-t0-*.json` (после исправлений), по прогону — `darwin-<источник>-<hw>-<режим>-<к/с>fps-t<потоки>-*.json`, разбор по этапам — `attrib-darwin-*.json`, кадры 4K proxy — `spikes/results/s3/frames/*.jpg`.

## Что мерили

- **Исходники (синтетика, `spikes/s3_decode/sources.py`).** 1080p25 H.264, 20 Мбит/с, 240 с; 1080p50 H.264, 28 Мбит/с, 240 с; **«тяжёлая камера»: 1080p50 H.264, 80 Мбит/с (факт 80,4), keyint 1 с, B-кадры, `scroll` двигает весь кадр + шум, 90 с**; **4K30 HEVC main10, BT.2020 + HLG (`arib-std-b67`), 45 Мбит/с, 90 с, поворот −90° через display matrix (как портретная съёмка iPhone)**. Шум добавлен, чтобы битрейт был камерным (иначе `testsrc2` декодируется нереально быстро), а в левом верхнем углу *сохранённого* кадра нарисован белый квадрат для проверки ориентации.
- **Что синтетика значит для нагрузки.** При равном битрейте декодирование (CABAC) сравнимо с камерным; движения в 20- и 28-Мбит/с клипах почти нет, поэтому компенсация движения у них лёгкая. Синтетика не «худший случай»: реальные камеры дают 50 Мбит/с на 1080p50 (Sony XAVC S) и 100 Мбит/с на 4K, и 80-Мбит/с клип показал в 2 раза меньше скорости, чем 28-Мбит/с. Правдоподобно пессимистична только кодировка proxy шума (x264 на шуме тяжелее, чем на обычной картинке). Не проверено: AVCHD 1080i (.MTS, чересстрочный, в графе нет деинтерлейса), VFR.
- **4K HLG — синтетика.** Пиксели — SDR-картинка, помеченная как HLG; совпадают только теги, кодек и поворот. **Реального файла с телефона и реального файла с камеры пока нет, шаг брифа «по одному реальному файлу каждого типа» остаётся открытым** (`bench_decode --real метка=путь`).
- **Один вызов ffmpeg, три выхода** (`single_pass.py`): `proxy.mp4` (libx264 veryfast, CRF 26, `-g` = 1 с, CFR по ближайшей стандартной частоте, 540 по *короткой* стороне, теги BT.709), `audio.wav` (pcm_s16le, 16 кГц, моно), `rawvideo` gray 160×90 (90×160 для портрета) 4 к/с в `pipe:1`. `-progress` идёт в stderr и разбирается в потоке. Python читает pipe порциями по 64 кадра (≈ 0,9 МБ), копит метрики и пишет `frames.npz`.
- **Режимы:** `full` (читать и считать), `none` (без выхода в pipe); `drain` (читать и выбросить) в основном прогоне уже не гонялся. Разница `full` / `none` показывает, тормозит ли Python ffmpeg. В первом прогоне были `drain` и `full` при 25 к/с метрик (запас по нагрузке на Python); их числа остались в тексте ниже, JSON этих прогонов перезаписан.
- **Декодирование:** CPU и `-hwaccel videotoolbox` (на Windows — `d3d11va`). **Проверка, что аппаратное декодирование реально включилось** (`hw_active`): перед прогоном 1-секундное декодирование с `-loglevel debug` и разбор строки `Format … chosen by get_format()` (аппаратный формат вроде `videotoolbox_vld`, `d3d11`, `cuda`), плюс сам прогон идёт с `-loglevel warning`, и строки `Failed setup for format … hwaccel initialisation returned error` ставят `hw_fallback_warning`. Прогон с `hw_active=false` не даёт вердикта по скорости и «приросту GPU». Дополнительно `ffmpeg_cpu_vs_software` (доля CPU ffmpeg от программного прогона; > 0,9 — подозрительно).
  - Демонстрация на Mac (`spikes/results/s3/darwin-hw-fallback-demo-*.json`): для MPEG-4 part 2 `-hwaccel videotoolbox` даёт rc=0 и молча считает на CPU; детектор показывает `hw_active=false`, `hw_fallback_warning=true`. Для H.264 и HEVC `hw_active=true`, формат `videotoolbox_vld`, доля CPU ffmpeg 0,25–0,54.
- **Измерения:** время стены / длительность медиа (× реального времени); CPU ffmpeg (rusage ребёнка на POSIX, выборка на Windows) и Python (`cpu_times`) в % одного ядра; пик RSS ffmpeg и Python (psutil, 0,1 с) и пик суммы. На Windows берётся максимум из рабочего набора и `private` (рабочий набор под нехваткой памяти ужимается).
- **Проверка выходов** на каждом прогоне: кодек, размер (короткая сторона 540), `pix_fmt`, теги цвета proxy, отсутствие остаточного поворота, квадрат в ожидаемой четверти кадра, wav 16 кГц моно. Для HDR-входов ещё перцентили яркости (p1/p50/p99), доля «пересвета» и JPEG кадра proxy в `spikes/results/s3/frames/`.

**Куда уходит время** (первые 60 с, `attribute.py`; M1, CPU). 1080p25 20 Мбит/с: только декодирование 18,5×; + масштаб до 540p 16,7×; + x264 ultrafast 15,0×; superfast 12,3×; veryfast 12,1×. 1080p50 80 Мбит/с: декодирование 5,8×, масштаб 5,4×, x264 ultrafast 4,9×, superfast 4,4×, veryfast 4,1×, то есть **декодер уже сам не дотягивает до 12×**, и пресет x264 тут ничего не спасёт. 4K HEVC 10 бит: декодер 3,3×, масштаб 2,9×, x264 2,7–2,8×. Рычаги: аппаратное декодирование для 4K; для тяжёлых H.264 на CPU рычага нет, кроме числа ядер.

**Ограничение потоков** (`--threads N`: `-threads`, `-filter_threads`, `-filter_complex_threads` и потоки x264; 1080p25 20 Мбит/с, CPU): без ограничения 11,1×, `--threads 4` — 10,4× (CPU ffmpeg всё ещё ~690% — это не настоящий лимит ядер), `--threads 2` — 6,6× (325%). То есть потоки ffmpeg — грубая замена «часть ядер занята распознаванием»; настоящий лимит даст только прогон вместе с нагрузкой S1.

## Бюджет анализа и распознавание речи (§5.3)

**Все цифры времени здесь — этап 1 + 1b отдельно, когда он один занимает все ядра** (ffmpeg 750% на 8 ядрах M1). §5.3 получает «20–25 минут» за счёт того, что распознавание речи на CPU идёт **параллельно** этапу 1 на тех же ядрах; этого здесь не измерено и нельзя вывести: общее время ≥ времени этапа 1 + доля конкуренции за ядра. Поэтому 20 мин для 1080p25 — **нижняя граница, не подтверждение бюджета**. Общий бюджет решается после S1 (скорость и потребление ядер ASR) прогоном S3 вместе с нагрузкой S1 на 5600H (6 ядер / 12 потоков); пока бюджет §5.3 — **не подтверждён**. Чисто для декодирования ожидаемое время на M1: см. колонку «3 ч 40 мин сырья» выше.

## Тонемаппинг (HLG → SDR)

**В Homebrew-сборке нет `zscale` (нет libzimg)**, поэтому на Mac работал только **запасной путь**: `colorspace=all=bt709:iall=bt2020` с принудительной пометкой BT.709 (HLG-сигнал трактуется как гамма BT.709; штатная «обратная совместимость» HLG, но без сжатия светов). Путь `zscale+tonemap` (hable) собран, но **не запускался ни разу**: `zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p`. Масштаб до 540p идёт *до* тонемаппинга (в 4 раза дешевле). `--tonemap auto` выбирает путь по `ffmpeg -filters`.

**Что измерено по пикселям.** Тегов недостаточно (`setparams` ставит BT.709 при любой картинке), поэтому есть синтетический HLG-кадр «рампа» (`make_hlg_ramp`): СИГНАЛ HLG растёт от 0 до 1 слева направо (10-бит limited range), и `bench_decode` прогоняет его через каждый доступный путь, проверяя proxy по яркости: чёрный ≤ 24, монотонность, доля пересвета (≥ 234) ≤ 2%, разделение светов (колонки 93–97% против 83–87%) ≥ 3 уровней, размах p99−p1 ≥ 100. Запасной путь проходит: p1/p50/p99 = 18/125/232, пересвет 0,4%, разделение 21,9, чёрный 18 (`darwin-hdr-ramp-*.json`). Это проверка «картинка не сломана» (нет плато, нет подъёма чёрного), а **не** проверка правильности яркости или цвета; для `zscale` результат появится только на Windows.

**Что НЕ измерено:** правильность тонемаппинга на 4K-клипе: его пиксели SDR с HLG-тегами, поэтому проверка пикселями на нём невозможна (в JPEG кадра 4K пересвет 15,8% — это белый маркер ориентации, а не ошибка преобразования). **Верность тонемаппинга реального iPhone-файла остаётся НЕИЗМЕРЕННОЙ**: JPEG кадра proxy (`spikes/results/s3/frames/*.jpg`) и сравнение запасного пути с `zscale` на реальном файле нужно оценить глазами.

## Решения (предварительные)

- **Proxy: 540 по короткой стороне**, h264 veryfast CRF 26, `-g` = 1 с. Для 4K и портрета выход 540×960 при тех же затратах, что 960×540. Пресет `superfast`/`ultrafast` помогает только лёгким файлам (+3–25% на 1080p25), на тяжёлых упираемся в декодер.
- **Метрики: 4 к/с, 160×90.** Python съедает 1–3% ядра; 25 к/с стоили бы 4–14% — запас огромный, но выигрыша для детектора сцен и качества кадра нет.
- **ETA по умолчанию:** пока нет данных с эталонного ПК, статический профиль без GPU: **10× для 1080p ≤ 30 к/с до ~25 Мбит/с, 5× для 1080p50 или > 40 Мбит/с, 3× для 4K HEVC**; с `d3d11va` на 4K — 4×. Профиль по битрейту: скорость растёт при падении битрейта файла, поэтому первая оценка берётся из `bit_rate` по ffprobe. Первая оценка по §5.1 всё равно перезаписывается измеренной скоростью после 60 с работы.
- **Ожидаемое время анализа 3 ч 40 мин сырья (этапы 1 и 1b, без параллельного ASR)** по числам M1: 1080p25 20 Мбит/с ≈ 20 мин, 1080p50 28 Мбит/с ≈ 32 мин, 1080p50 80 Мбит/с ≈ 59 мин, 4K ≈ 52–79 мин. Для §5.3 (15× = 15 мин) это хуже в 1,3–4 раза; окончательные числа — с Windows и реальными файлами.

## Риски и что не проверено

- **Не измерено на Windows**: ни `d3d11va`, ни реальный CPU эталонного ПК, ни `zscale`. M1 с 8 быстрыми ядрами и Ryzen 5 5600H (6 ядер / 12 потоков, при ~6 ГБ ОЗУ) несравнимы.
- **Нет реальных файлов** с камеры и телефона. Синтетика тяжёлая по битрейту, но не по настоящему содержимому. 4K HLG-пиксели — не HLG.
- **Скорость сильно зависит от битрейта камеры** (3,7× при 80 Мбит/с, 6,9× при 28 Мбит/с на M1); пороги 12×/15× нельзя применять без привязки к битрейту.
- **Бюджет с параллельным распознаванием речи не измерен** (раздел выше).
- **VFR, AVCHD 1080i (.MTS) и неровные таймстемпы** не проверены: `fps=` в графе приводит к ближайшей стандартной частоте.
- **Поворот** проверен только для −90° на синтетике (180° — только функция ожидания). Файл без звука проверен тестом (нет wav, rc=0).
- Память на ноутбуке с ~1,5 ГБ свободной ОЗУ: ffmpeg 4K HEVC занимал 663–723 МБ, 1080p — 125–245 МБ, Python 36–70 МБ. Для 3 ч 40 мин метрики занимают ≈ 2 МБ в `npz` (52 800 кадров × 4 float32) и ≈ 7 МБ в списках Python. Генерация 4K-исходника x265 на ноутбуке может не влезть и идёт ≈ 10 мин даже на M1.
- Скорость Mac при зафиксированной температуре и параллельной нагрузке не контролировалась; на Mac `--repeat 1`.

## Как запустить на Windows-ПК (эталонный ноутбук)

Ryzen 5 5600H, GTX 1650, ~6 ГБ ОЗУ, ffmpeg 9.0.2 gyan full, репозиторий `C:\Users\oshis\mojo_studio`. Все команды работают и в `cmd`, и в Windows PowerShell 5.1 (через SSH он включён по умолчанию): пустых аргументов нет, `--only` принимает `all`/`none`/список.

```
cd C:\Users\oshis\mojo_studio
.venv\Scripts\pip install -e ".[dev,spikes]"
ffmpeg -hide_banner -filters | findstr zscale
```

Исходники весят ~3 ГБ и генерируются долго (особенно 4K), поэтому лучше скопировать с Mac готовые `spikes/data/s3/h264_1080p25.mp4`, `h264_1080p50.mp4`, `h264_1080p50_xavc.mp4`, `hevc_4k_hlg_rot.mp4`, `hlg_ramp.mp4` (существующий файл с неправильной длительностью пересоздаётся, поэтому при копировании с другими `--dur-*` см. следующую строку). Иначе — короткие версии:

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --prepare-only --dur-1080 120 --dur-xavc 60 --dur-4k 40
```

Основной прогон (CPU и `d3d11va`, режимы `full` и `none`, повторы по кругу — для ноутбука `--repeat 3`; ~25–40 мин). На ноутбуке с ~1,5 ГБ свободной ОЗУ закройте браузер и прочее. **Если брали короткие версии, во всех командах ниже укажите те же `--dur-1080/--dur-xavc/--dur-4k`**, иначе файлы пересоздадутся:

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --hwaccels none,d3d11va --modes full,none --repeat 3
```

Реальные файлы: положите в UTF-8-файл `real.txt` строки `метка=путь` (метки латиницей; пути с кириллицей лучше писать в файл, а не в командную строку — кодовая страница консоли по SSH портит буквы), например:

```
camera=D:\Свадьба\камера 1\C0001.MP4
iphone=D:\Свадьба\телефон\IMG_0001.MOV
```

```
.venv\Scripts\python -m spikes.s3_decode.bench_decode --only none --real-file real.txt --hwaccels none,d3d11va --repeat 3
```

Разбор по этапам, одиночный проход и «часть ядер занята» (грубая замена параллельному ASR; настоящую проверку делать с нагрузкой S1):

```
.venv\Scripts\python -m spikes.s3_decode.attribute spikes\data\s3\h264_1080p50_xavc.mp4
.venv\Scripts\python -m spikes.s3_decode.attribute spikes\data\s3\hevc_4k_hlg_rot.mp4 --hwaccel d3d11va
.venv\Scripts\python -m spikes.s3_decode.bench_decode --only h264_1080p25 --hwaccels none --modes full --threads 6 --no-ramp
.venv\Scripts\python -m spikes.s3_decode.single_pass "D:\Свадьба\клип.mp4" --out-dir "D:\out" --hwaccel d3d11va --tonemap zscale
```

Сначала запускать без GPU и с GPU на одном и том же ПК, затем (если есть) на машине без дискретной карты. Коммитить только `spikes/results/s3/*.json` и `spikes/results/s3/frames/*.jpg`, не `spikes/data/`. Что смотреть:

- `x_rt` в `summary-win-*.json` против 12 / 15 **с учётом `bit_rate_mbps` файла**; `tonemap` должен быть `zscale`.
- `hw_active` у строк `d3d11va` обязан быть `true` (иначе вердикт по GPU недействителен: драйвер, iGPU вместо GTX 1650, профиль HEVC 10 бит); `hw_cpu_suspicious` = `true` тоже означает, что аппаратное декодирование, вероятно, не работает. `d3d11va` на H.264 может оказаться медленнее CPU, как videotoolbox на Mac.
